# AGENTS.md — Deployr

Guidance for AI coding agents (Claude Code, Codex, Cursor, etc.) working in this repo.
Read this fully before making changes.

## 1. What this project is

Deployr is a fast, TypeScript-only CLI for producing **client-ready website audits**.
It runs HTML/SEO checks, security header checks, and Lighthouse, stores results in
per-client workspaces, and generates a client-facing report and email.

Primary users: freelancers and small agencies who audit a client site, then send a report.
Optimize for: **repeatable, readable, client-presentable output**, not raw technical dumps.

## 2. Runtime and language constraints (important)

- **Node.js 24+**. TypeScript runs **directly**, with no build step and no bundler.
- Because there is no compile step, write **erasable TypeScript only**:
  - No `enum`, no `namespace`, no constructor parameter properties.
  - Use `import type` for type-only imports.
  - Use explicit file extensions in relative imports (`./checks.ts`, not `./checks`).
- Do not add a build tool, transpiler, or `dist/` output without being asked.
- Keep dependencies minimal. Justify any new runtime dependency in your PR/summary.
- Lighthouse checks need a local Chrome, Chromium, Edge, or Brave. Never assume one exists in CI or tests.

## 3. Commands

User-facing CLI surface (keep behavior stable):

| Command | Purpose |
|---|---|
| `deployr <url>` | Full audit: HTML + security + Lighthouse, printed to terminal |
| `deployr <url> --save [folder]` | Same, and save Markdown reports into a workspace |
| `deployr check [url]` | HTML/SEO check only |
| `deployr security [url]` | Security headers check only |
| `deployr lighthouse [url]` | Lighthouse check only |
| `deployr new` | Interactive: create a client audit workspace |
| `deployr list` | List workspaces |
| `deployr inspect <latest\|workspace>` | Inspect or update a workspace |
| `deployr report <latest\|workspace>` | Build `final-report.md` and `client-email.md` |

Dev commands: **check `package.json` for the exact script names** and use those.
Do not invent scripts. If tests exist, run them before declaring work done.

## 4. Architecture (module map)

```
src/
  cli.ts          Argument parsing, prompts, command routing, high-level flow
  checks.ts       Fetch + HTML analysis + security analysis + CLI/Markdown formatters
  lighthouse.ts   Browser discovery, Lighthouse run, summarize, CLI/Markdown formatters
  workspace.ts    Workspace templates, create/list/read/write, section updates
  report.ts       Load agency config, build final report + client email
  ui.ts           Terminal helpers: prompts, progress, color, error display
```

Responsibilities (keep these boundaries):

- `cli.ts` **routes and orchestrates only**. No analysis logic here.
- `checks.ts` / `lighthouse.ts` **analyze and format**. They must not read or write workspaces.
- `workspace.ts` owns **all filesystem layout** under `audits/`. Other modules go through it.
- `report.ts` consumes workspace files plus config and produces client documents.
- `ui.ts` owns **all terminal presentation**. Do not scatter ANSI codes elsewhere.

Pattern to follow: each check has an **analyze** function (returns data), a **CLI formatter**
(colorized terminal block), and a **Markdown formatter** (for saved reports).
Keep analysis (pure, testable) separate from formatting.

## 5. Workspaces and data model

Workspaces live in `audits/<date>-<slug>/` (one per client or audit).

Typical files:

- `brief.md`, `workspace.md`, `findings.md` — created from templates by `deployr new`
- `raw/lighthouse.json` — raw Lighthouse output when saving
- Markdown summaries for HTML, security, and Lighthouse checks
- `final-report.md`, `client-email.md` — generated by `deployr report`

`AuditInput` (in `workspace.ts`) captures: client name, slug, URL, business type, goals,
pages, concerns, etc. It is rendered into `brief.md` and `workspace.md`.

Rules:

- `latest` is a supported shortcut for the most recent workspace. Preserve it.
- Workspaces are **user data**. Never delete, overwrite, or reformat existing audit files
  unless the command's purpose is to update that specific file or section.
- `audits/` content is client-confidential. Never commit real client data, and never use
  real client data in tests or fixtures.

## 6. Configuration

`deployr.config.json` (legacy name: `shipsafe.config.json`, still supported) provides:

- `agencyName`, `auditorName`
- Service pricing: audit, refresh, growth

This feeds the report's "Recommended Next Step" and pricing sections and the client email.
Keep the legacy filename working. Do not remove it without a deprecation path.

## 7. Report structure

`final-report.md` sections, in order: Context, Scorecard, Automated Check, Security Check,
Lighthouse Check, Findings, Page Reviews, Recommended Next Step (plus pricing/agency details).

Changing section order or names is a **user-visible change**. Call it out explicitly.

## 8. Coding conventions

- Strict TypeScript. No `any` unless unavoidable and commented.
- Prefer small pure functions, plain objects, and explicit return types on exported functions.
- Errors: fail with a clear, actionable message through `ui.ts`. Do not dump stack traces
  at end users. Network failures, bad URLs, and missing browsers are **expected** cases.
- Output tone: client-presentable. Plain language, severity-ordered, no jargon without explanation.
- Do not add emojis or decorative output to saved Markdown reports.
- Match the existing style of the file you are editing.

## 9. How to add a new check

1. Add the analyzer in `checks.ts` (or a new module if it is large). It returns structured data.
2. Add a CLI formatter and a Markdown formatter next to it.
3. Wire a command in `cli.ts` and include it in the full-audit flow if appropriate.
4. Include it in `--save` output and in `report.ts` (new report section or scorecard entry).
5. Add unit tests for the analyzer using static HTML/header fixtures, with no live network calls.
6. Update the README command table.

## 10. How to add a new command

1. Add parsing and routing in `cli.ts`.
2. Put logic in a module, not in `cli.ts`.
3. Support `--save` semantics consistently if the command produces results.
4. Update the README and `--help` text.
5. Add a CLI parsing test.

## 11. Testing

- Tests cover: HTML analysis, security analysis, CLI parsing, workspace templates, Lighthouse summary scaffolding.
- **No live network and no real browser in tests.** Use fixtures and mocked responses.
- Lighthouse: test the summarizer against a saved sample JSON, not by launching Chrome.
- Add or update tests for any behavior change. Run the full suite before finishing.

## 12. Boundaries for agents

**Do**
- Make focused, minimal diffs. Explain the reasoning briefly in your summary.
- Preserve command names, flags, file names, and output paths unless asked to change them.
- Ask before large refactors, new dependencies, or changing report structure.

**Do not**
- Add a build step, bundler, or non-erasable TS syntax.
- Run audits against real third-party sites in tests or scripts.
- Commit anything under `audits/` or any secrets and API keys.
- Silently change report wording or pricing logic. These are client-facing.
- Mix terminal formatting into analyzers, or filesystem access into checks.
